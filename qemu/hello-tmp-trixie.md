# Provisioned /tmp Across a Real Boot on Debian 13 (qemu, debian)

## Overview

This exercise repeats the experiment from `qemu/hello-image.md` on a newer base. A shell provisioner writes `Hello, World!` to `/tmp/hello.txt` and installs `tree`, and the question is what the resulting qcow2 actually contains. The builder is still `qemu`, and the artifact is still a bootable disk image. The base is now Debian 13 (trixie): the `genericcloud` qcow2 from the dated directory `20261001-2618` (debian_version 13.7, systemd 257.13), pinned by the SHA512 from that directory's `SHA512SUMS`. On Debian 12 the file reached the disk and was deleted at the artifact's first boot. On Debian 13 it never reaches the disk at all, because `/tmp` is a RAM-backed filesystem during the build boot itself. That is the fourth "fate" listed in `qemu/hello-image.md`'s section "The three possible fates of /tmp", which was reasoned about there but not observed until now.

## How trixie sets up /tmp

Two pieces of trixie's boot configuration decide the outcome. Both were read from inside the base image, and they differ from bookworm. The first is a mount unit, `/usr/lib/systemd/system/tmp.mount`, which mounts a tmpfs at `/tmp`. A tmpfs is a filesystem that lives entirely in RAM: writes to it never touch a disk, and its contents vanish when the machine powers off. The unit sets `DefaultDependencies=no` and `Before=local-fs.target`. It is enabled by a vendor symlink at `/usr/lib/systemd/system/local-fs.target.wants/tmp.mount`, so it runs very early on every boot without any configuration in `/etc`, and `/etc/fstab` has no `/tmp` entry that could override it. Mounting a filesystem at a directory hides whatever that directory holds on the underlying disk without deleting it. The Debian 13 release notes describe this change in §5.1.6.

The second piece is the tmpfiles rule. Bookworm shipped `D /tmp 1777 root root -`, while trixie ships `q /tmp 1777 root root 10d` in `/usr/lib/tmpfiles.d/tmp.conf`. According to tmpfiles.d(5), `q` behaves like `v`, and on a filesystem that is not btrfs, `v` behaves like `d`. The root filesystem here is ext4, so `q` is effectively `d`. `d` lacks the extra behavior of `D`, which empties the directory when `systemd-tmpfiles --remove` runs. All `d` has is age-based removal, and that happens only under `--clean`, which `systemd-tmpfiles-clean.timer` triggers (first run 15 minutes after boot). The boot-time `systemd-tmpfiles-setup.service` runs `--create --remove --boot` after `local-fs.target`, and on trixie it removes nothing from `/tmp`.

## Observable behavior

`packer validate` and `packer fmt -check` both pass on the final template. Each of the two independent builds took about 24 seconds. In both build logs, the first provisioner's `findmnt /tmp` printed `/tmp tmpfs tmpfs rw,nosuid,nodev,nr_inodes=1048576,inode64` before `Hello, World!` appeared. The artifact is `output-hello-tmp-trixie/packer-debian13`, a qcow2 with a 40 GiB virtual size. Build one produced 1349517312 bytes and build two produced 1343094784 bytes, so the two builds are not byte-identical.

Each artifact was booted once with `-snapshot` and a verification seed under `.tmp/` that created a sudo-capable `verify` user. On both boots `findmnt /tmp` reported a tmpfs that held only directories created at boot. After `sudo umount /tmp`, `findmnt /tmp` exited 1, and `ls -la /tmp` listed only `.` and `..`, with the directory itself `drwxrwxrwt root root` and an mtime of `Oct 1 04:57`, which is the date the base image was built rather than the day of the build. On both boots `tree --version` printed `tree v2.2.1`, `passwd -S packer` showed `L`, `/etc/ssh/sshd_config.d/` was empty, and `sshd -T` reported `passwordauthentication no`.

## Internal mechanism

The build VM boots from a copy of the trixie base, so `tmp.mount` runs in the build boot just as it would in any other boot. The tmpfs is in place at `local-fs.target`, long before cloud-init creates `packer` and sshd accepts Packer's connection. When the first provisioner runs as root through `execute_command`, `tee` writes `hello.txt` into that tmpfs, so the bytes sit in guest RAM. The shell provisioner's own uploaded script also lands in this tmpfs, because its default `remote_folder` is `/tmp`. `apt-get install tree` writes to the ext4 root, which is the guest's virtual disk. The cleanup provisioner then locks `packer` and deletes cloud-init's `50-cloud-init.conf`, the drop-in that `ssh_pwauth: true` had generated. The graceful `shutdown_command` flushes cached disk writes and powers off, discarding RAM and the tmpfs with it. Packer then converts the disk. The on-disk `/tmp` beneath the mount was never written, so the qcow2 holds the base image's empty `drwxrwxrwt` directory unchanged.

The mtime is what makes this a positive result rather than an absence. A directory's mtime changes whenever a name is added to it or removed from it. Had `hello.txt` been written to disk and later deleted, whether during the build or at boot as on Debian 12, the on-disk `/tmp` would carry the build day's date. It still carries the base image's date, so no entry was ever added. The installed `tree` is the control: it shows that the provisioner did run as root and did write to persistent storage, and that only the write under `/tmp` vanished.

## Design rationale

`findmnt /tmp` runs before the write so that the build log itself records which filesystem the write is about to land in. Nothing remounts `/tmp` partway through a provisioner, so placing it after the write would show the same thing, but placing it first reads as evidence for that write. The credential lock is a separate, final provisioner. NOPASSWD sudo never consults the password, so locking it does not affect sudo. What the password does gate is a fresh SSH login, which a later reconnect (an `expect_disconnect` step, a reboot, a dropped session) would need. Locking last keeps every earlier step able to log in and still leaves the artifact locked, a pattern carried over from `qemu/hello-image.md`.

The broader lesson concerns placement, not mechanism. `/tmp` promises nothing about persistence, and on trixie two independent mechanisms enforce that. Masking `tmp.mount` would not make a provisioned file safe: the `q ... 10d` rule ages files by their own timestamps, which are set at build time. An image first booted three weeks after it was built would therefore lose the file on the first `--clean` run, about 15 minutes after boot. A file that must survive into the artifact belongs outside `/tmp`.

## Edge cases

The verification boot initially came up with no network interface, only `lo`, because plain `-nic user` gives the guest QEMU's default e1000 card and the genericcloud kernel has no driver for it. Adding `model=virtio-net-pci` fixed it. Packer's qemu builder defaults to virtio networking, so the build itself never hit this. The output directory name comes from the template's explicit `output_directory = "output-hello-tmp-trixie"`. The default naming was therefore not exercised this session, although `qemu/hello-image/`'s `output-hello` (build name `hello-image`, source label `hello`) suggests that the default follows the source label. The disk file name `packer-debian13` does follow the source label. Packages are unpinned, so the two artifacts differ in size even though both were built from the same template.

## Worked example

Trace the second build and its check. The builder copies the cached trixie base into `output-hello-tmp-trixie/packer-debian13`, attaches the `CIDATA` CD and boots. systemd reaches `local-fs.target` through `tmp.mount`, so `/tmp` becomes a fresh tmpfs layered over the empty on-disk directory dated Oct 1. `systemd-tmpfiles-setup` applies `q /tmp`, which on ext4 only ensures the directory exists. cloud-init then creates `packer`, and Packer connects. The first provisioner prints the tmpfs line from `findmnt`, writes `hello.txt` into RAM, and installs `tree 2.2.1-1` onto ext4. The second locks `packer` and deletes the drop-in. `sudo shutdown -P now` flushes the disk and drops RAM, and Packer converts the image.

Booting that file with `-snapshot` and the `iid-verify-01` seed mounts a new, empty tmpfs at `/tmp`, so `ls` finds only boot-time directories. `umount /tmp` exposes the disk's own directory: it contains only `.` and `..` and still carries the Oct 1 mtime, so nothing was ever created in it. `tree` runs, `packer` is locked and password authentication is off, which completes the claim that the image received the provisioner's persistent writes and nothing under `/tmp`.
