# Owned sshd Drop-in for Password Policy (qemu, debian)

## Overview

This exercise starts from the qemu artifact in `qemu/hello-key-var.md`, a Debian 12 genericcloud qcow2 with a key-only `guest` account and a locked `packer` build account, and changes what keeps password SSH off in it. That template turned password login off by deleting cloud-init's `/etc/ssh/sshd_config.d/50-cloud-init.conf`, so the policy rested on a file being absent and on the base `sshd_config` happening to say `no`. Here the template ships its own drop-in, `01-ssh-dropin.conf`, containing `PasswordAuthentication no`, and the claim the image makes is narrower and testable: it ships with password SSH login disabled, and keeps it disabled when a later instance's cloud-init sets `ssh_pwauth: true`. A consumer who runs their own root commands through `write_files` or `runcmd` is outside that claim. The `file` provisioner appears here for the first time, and it is the one genuinely new Packer mechanism; everything else in the template is carried over from `qemu/hello-key-var/` and cited rather than re-derived.

## Drop-in ordering

`qemu/hello-image.md` already established the rule this exercise rests on: Debian's `sshd_config` includes `sshd_config.d/*.conf` before its own `PasswordAuthentication no`, and sshd keeps the first value it reads for each keyword. The new piece is what happens when that glob matches several files. sshd reads them in lexical order of their filenames, compared character by character by code, not as numbers. That is why `100-local.conf` sorts before `50-cloud-init.conf` (`1` before `5`), and why `5-local.conf` also sorts before it: the names first differ at the second character, where `-` (code 45) comes before `0` (code 48). A fixed-width two-digit prefix such as `01-` makes string order and numeric order agree, which is the reason for the `NN-` convention. A name that does not end in `.conf`, such as `01-local`, is never read at all, however early it sorts.

## Observable behavior

`packer fmt -check` passed on every version of the template checked during the session, and the second build ran as `make clean validate fmt build`, which printed `The configuration is valid.` before building. The first build, on 2026-10-06, finished after 1 minute 15 seconds; the second, on 2026-10-07 from a deleted `output-hello`, finished after 26 seconds because the pinned base image was already cached. Both logs show `Uploading 01-ssh-dropin.conf => /tmp/01-ssh-dropin.conf` between the key provisioner and the install step, and `passwd: password changed.`, which is how `passwd -l` reports the lock.

The first artifact was booted with `-snapshot` and a copy of the build's own seed, so the same `instance-id`. As `guest`, `ls -l /etc/ssh/sshd_config.d/` showed only `01-ssh-dropin.conf`, owned by root with mode 644 and 26 bytes, and a password-only SSH attempt as `packer` was answered with `Permission denied (publickey)`. Both artifacts were then booted with a new-instance seed (`iid-verify-01`, `ssh_pwauth: true`, and a `verify` user with sudo that exists only for verification). On each, `50-cloud-init.conf` was back, mode 600, containing `PasswordAuthentication yes`, while `sudo sshd -T` printed `passwordauthentication no`, and `journalctl -u ssh` held exactly one `Accepted password for packer` line. On the second artifact's new-instance boot, the password-only attempt as `packer` was again refused with `(publickey)` only, and `guest` logged in by key as `uid=1001(guest)` with `sudo` demanding a password.

## Internal mechanism

The `file` provisioner only transfers a file, here from the host to the guest; it runs no command, so it has no `execute_command` and the upload happens as the communicator user, `packer`. Its `source` is relative to the directory Packer runs in, the same caveat `qemu/hello-image.md` records for `cd_files`. Because `packer` cannot write into the root-owned `/etc/ssh/sshd_config.d/`, the file lands in `/tmp`, and the next shell provisioner, running as root through the same `sudo sh -c` `execute_command` described in `qemu/hello-image.md`, runs `install -o root -g root -m 644` into the drop-in directory and then `rm -f` on the staged copy. `install` writes a new file with the owner and mode the template names, so neither is inherited from the upload. The cleanup provisioner then locks `packer` and still deletes `50-cloud-init.conf`.

None of this cuts off the build. sshd reads its configuration again only on a restart or a reload, and nothing in the build does either, so the new policy never applied to Packer's own session. The single `Accepted password for packer` line on each artifact is the evidence that Packer opened one SSH connection for the whole build, shutdown included; that also implies the build's journal reached the disk, since the line came from the build boot.

On a new instance, cloud-init's per-instance modules run again, and `ssh_pwauth: true` rewrites `50-cloud-init.conf` with `yes`. sshd still reads `01-ssh-dropin.conf` first, so its `no` is the first value and the effective setting does not change.

## Design rationale

Deleting `50-cloud-init.conf` alone worked only until the next new instance: cloud-init writes the file again, the `Include` puts it ahead of the base file's `no`, and password login returns. That was reasoned through rather than built here, from the behavior observed on this exercise's own new-instance boots. Owning an earlier-sorted drop-in makes the image's own file decide. The deletion was kept anyway, so the image ships without a contradictory setting, but it no longer carries any part of the guarantee.

Two policies were weighed. Default would ship with password login off but honor a consumer's explicit `ssh_pwauth: true`, on the argument that whoever re-runs cloud-init with that setting takes responsibility for the result. Enforce, which was built, refuses password login despite that request. It gives a claim a boot can falsify, and it is what separates this artifact from `hello-key-var`. Its cost is that a consumer sees `50-cloud-init.conf` saying `yes` while password logins are denied, and has to act as root, for example with a `runcmd` that deletes `01-ssh-dropin.conf`, to get password login back.

## Edge cases

With `packer` locked and `guest` unprivileged, no account on the artifact can run `sudo`. `sshd -T` therefore could not run on the same-seed boot, which is why that boot relied on the method list in the `Permission denied (...)` reply instead, and why the new-instance seed added a sudo-capable verification user. A drop-in named to sort after `50-` (say `99-local.conf`), or one missing the `.conf` suffix, would leave the template building cleanly while the new-instance boot showed `passwordauthentication yes`.

## Worked example

Trace the second artifact's new-instance boot. QEMU starts `output-hello/packer-hello` with `-snapshot` and `.tmp/seed-new.iso` attached. cloud-init's NoCloud datasource reads `meta-data`, sees `iid-verify-01`, which this disk has never recorded, and runs its per-instance modules. It creates `verify` with a key and passwordless sudo, and because of `ssh_pwauth: true` it writes `PasswordAuthentication yes` into a fresh `50-cloud-init.conf`, timestamped 09:25. sshd starts and reads `sshd_config`. At the `Include` line it expands `sshd_config.d/*.conf` to `01-ssh-dropin.conf` then `50-cloud-init.conf`, since `0` sorts before `5`. The first `PasswordAuthentication` it meets is the `no` written at build time by `install` as root:root 644, so the later `yes` is ignored. `sudo sshd -T` as `verify` prints `passwordauthentication no`, and a password-only login as `packer` is answered `Permission denied (publickey)`, with `password` not offered at all. Either `passwordauthentication yes` or a denial listing `password` would have falsified the claim, and neither appeared.
