# Checksum and Compress Post-Processors on a Disk Image (qemu, debian)

## Overview

This exercise builds a Debian 13 genericcloud disk image with the qemu builder. Instead of leaving the qcow2 in its output directory, it hands the image to a two-step post-processor sequence. `compress` packs the disk into `.tmp/trixie13.tar.gz` and lets Packer discard the original. `checksum` then writes a SHA-512 line for that archive into `.tmp/trixie13.tar.gz.sha512`. The intuition is that of a release pipeline: the archive and its checksum are what a downloader would receive, so verification checks the checksum, extracts the archive, and boots the extracted disk. Booting the original qcow2 would prove nothing, because nobody receives it. This is the cross-target counterpart of `docker/hello-tagged-chain.md`. The interesting difference is that the qemu builder's artifact is a file on disk, while the docker builder's artifact is an image held by the daemon. The source block and provisioners are a near-verbatim reuse of `qemu/hello-tmp-trixie/`, so only the post-processor side is derived here.

## Records, not bytes, on a file-based builder

`docker/hello-tagged-chain.md` established that a sequence passes artifact records between steps, not image bytes. It also established that checksum iterates only the record's `Files()` list, which is `nil` for a docker image record. The question here was what the qemu builder's record carries. It should list the disk file it wrote, because a builder that has just written `output-qcow2-chain/packer-debian13` has a path to report. The build confirmed this indirectly. The builder's own record is never printed in the summary, because it was discarded. However, the archive's single member is named `packer-debian13`, and only the builder could have supplied that path to compress. So no `artifice` step is needed on qemu, which is the direct opposite of the docker case.

compress (built into Packer v1.16.2) archives every file in the record it receives. It writes to `output`, whose extension selects the format, so `.tar.gz` means a tar stream through parallel gzip. It returns a new record whose only file is the archive. Its source returns `newArtifact, false, false, nil`, so it does not force "keep" the way docker-tag does (see `docker/hello-tagged.md`). Packer core therefore applies the template's `keep_input_artifact = false`. It does so after compress returns, by destroying the builder's artifact, and for the qemu builder that removes the whole `output_directory`, not just the disk file. checksum then receives compress's record, so it hashes the archive and nothing else.

## Observable behavior

Four builds ran with the same template; only the Makefile changed between them. The first, from a clean tree, ended with two summary lines: `compressed artifacts in: .tmp/trixie13.tar.gz`, and `Created artifact from files: .tmp/trixie13.tar.gz, .tmp/trixie13.tar.gz.sha512`. Afterwards `output-qcow2-chain/` did not exist at all. The archive was 449,066,420 bytes and held one entry, `packer-debian13`, of 1,345,847,296 bytes with a 1970 timestamp, and the checksum file held one line. The second build ran with a `build: clean` prerequisite plus `mkdir -p .tmp` and produced a 452,099,680-byte archive and again one line. With the clean prerequisite removed, the third build overwrote the archive (449,109,095 bytes) but appended to the checksum file, which grew to two lines. `sha512sum -c` then printed `FAILED` for the stale line and `OK` for the current one, and exited 1. That build's summary listed only the archive under checksum's record. The fourth build restored `build: clean` without `mkdir -p .tmp`, and compress created `.tmp/` itself, giving a 452,209,596-byte archive with a one-line checksum.

The fourth build's archive passed `sha512sum -c` and was extracted into the repo's `.tmp/verify/`. `qemu-img info` reported a qcow2 with a 40 GiB virtual size and 1.26 GiB on disk. It was booted with `-snapshot`, a virtio disk and NIC, and a seed with the new instance ID `iid-verify-01` creating a key-only `verify` user with sudo and no `ssh_pwauth`. On that boot, `tree --version` printed `tree v2.2.1`. `su packer`, run as `verify` without sudo and given the password `packer`, printed `su: Authentication failure` and exited 1. `sudo sshd -T` printed `passwordauthentication no` and `kbdinteractiveauthentication no`, and `/etc/ssh/sshd_config.d/` was empty. An SSH attempt as `packer` with pubkey disabled was answered `Permission denied (publickey).`

## Internal mechanism

After provisioning, the builder halts the VM, converts the working disk into `output-qcow2-chain/packer-debian13`, and returns a record listing that file. compress calls `os.MkdirAll` on the directory of its target and then `os.Create` on the target. That is why a missing `.tmp/` is harmless here, while docker-save, which calls only `os.Create`, failed on the same precondition in the docker chain. `os.Create` truncates, so a rebuild replaces the archive. Once compress returns, core sees that keep is false and not forced, and destroys the builder's artifact. checksum receives the compress record, hashes `trixie13.tar.gz` once for `sha512`, and appends a line of hash, tab and base name to its output, which it opens with `O_APPEND|O_CREATE` and never truncates. It adds the output file to its returned record only when that file did not exist beforehand. That rule explains why the third build's summary listed the archive alone.

## Design rationale

compress comes before checksum because a downloader verifies the file they received, which is the archive. Checksumming the qcow2 first would hash a file that is then deleted. It would also hand compress a record containing both the disk and the checksum file. Doing the packaging inside the post-processor chain, rather than as a `tar` and `sha512sum` line in the Makefile, means compress learns the disk's path from the builder's own record. A Makefile line would have to hardcode `output-qcow2-chain/packer-debian13`, which breaks when the source label, output directory or builder changes. The cost is that per-plugin file handling becomes part of the build's behavior. compress creates directories and truncates its output, while checksum appends, and neither behavior appears in the docs. The stale-line hazard still needs a precondition outside the template, `build: clean`, so `make build` is repeatable but a bare `packer build` is not.

## Edge cases

checksum's append behavior makes a rebuild without cleanup silently produce a checksum file whose check fails, even though the archive itself is fine. The failure shows up only at verification time, not in the build. The two-line file from the third build is the concrete case. A related hazard concerns the access checks. A refused `packer`/`packer` SSH login cannot, by itself, show that `passwd -l` worked, because `passwordauthentication no` refuses every password whether it is valid or not. The lock therefore needs its own check through a password path that sshd does not control. Running `su` as root would not serve, because root's `su` asks for no password, so it has to run as an ordinary user. Finally, the behavior of a compress failure as the first step of the sequence was not observed here, so whether the qcow2 would survive it remains untested.

## Worked example

Trace the fourth build. Make runs `clean`, removing `.tmp` and `output-qcow2-chain`, then `packer build`. The builder downloads nothing new, because the base image is already cached. It copies and resizes the disk, boots it with the `CIDATA` seed, installs `tree`, locks `packer` and deletes `50-cloud-init.conf`, then halts and converts the disk into `output-qcow2-chain/packer-debian13`. Its record lists that one path. compress receives the record and creates `.tmp/`, which does not exist. It then tars `packer-debian13` through pgzip into `.tmp/trixie13.tar.gz` (452,209,596 bytes) and returns a record listing only the archive. Core then destroys the builder's artifact, and `output-qcow2-chain/` disappears. checksum receives the archive record and finds that `.tmp/trixie13.tar.gz.sha512` does not exist, so it creates it with one line, `8fd8ba6f…`, a tab and `trixie13.tar.gz`. It returns a record listing both files, which is the final summary line. On the host, `sha512sum -c` reports OK. The extracted disk then boots under the verification seed, shows `tree v2.2.1`, refuses `su packer`, reports `passwordauthentication no`, and answers SSH as `packer` with `(publickey)` only. Had the previous build's `.sha512` survived, the same trace would have appended a second line instead, and the check would have failed.
