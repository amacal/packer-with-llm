# Agent-Supplied SSH Key via an Input Variable (qemu, debian)

## Overview

This exercise starts from the qemu artifact in `qemu/hello-image.md`: a Debian 12 genericcloud qcow2 with a `guest` account that accepts exactly one SSH public key. It changes where that key comes from. In `hello-image` the key was a literal written into a shell provisioner's inline script, so every build of that template, by anyone, authorized the same key. Here the template declares an HCL2 input variable, `ssh_public_key`, and the key is supplied each time the build is invoked. The Makefile reads it from the invoking user's ssh-agent, cuts it down to its type and base64 fields, and passes it with `-var`. Everything else is reused unchanged and cited from `qemu/hello-image.md`. The new material is how a value travels from the invocation into a root shell in the guest, and the session showed two ways that trip can end with an empty value and a build that still reports success.

## Two templating layers

A shell provisioner in this template contains two string-templating syntaxes, and they are resolved by different components at different times. `${var.ssh_public_key}` is an HCL2 template sequence. Packer evaluates it on the host when it reads the template, before any VM exists, and the result is ordinary text. `{{ .Path }}`, `{{ .Vars }}` and `{{ .EnvVarFile }}` in `execute_command` are Go-template fields that only the shell provisioner fills in at run time. `{{ .Path }}`, for instance, is where the provisioner just uploaded the script inside the guest, so it cannot exist until the VM is up and Packer is connected over SSH.

## Observable behavior

`packer validate` reacts to the variable before anything boots. With no value supplied at all, it reports `Unset variable "ssh_public_key"`. With `-var ssh_public_key=` it reports the validation rule's message, `Variable ssh_public_key must start with 'ssh-'.`, attributed to `main.pkr.hcl:13`. An attempted `required = true` was rejected as `Unsupported argument`. `validate` also failed with `Output directory 'output-hello' already exists` while the previous artifact was still present, and it does not accept `-force`. `packer fmt -check` and `packer validate` both pass on the final template.

The first build whose `execute_command` sourced the env file outside `sudo` finished cleanly, in about 24 seconds, with no error. Its artifact nonetheless refused key 1 with `Permission denied (publickey)`. After the fix, the guest's `authorized_keys` held exactly one line, the key's type and base64 fields with no comment, key 1 logged in, and a password-only SSH attempt as `packer` was offered only `publickey`, as in `qemu/hello-image.md`. The final template, with a `wc -l` line added that prints `1` in the build log, was built twice through the then-current Makefile with `--force`, whose log shows `Deleting previous output directory...`. Built with key 2, its artifact accepted key 2 (exit 0) and refused key 1 (exit 255), and built with key 1 the opposite held.

## Internal mechanism

The variable block declares `type = string` and has no `default`, and that alone makes the variable required. Packer refused to evaluate the template with it unset, and in a throwaway check it did so even when nothing referenced the variable. The `validation` block's `condition` is `can(regex("^ssh-", var.ssh_public_key))`. An empty string counts as a set value, so it passes the required check. `regex` then raises an error because nothing matches, `can` turns that error into `false`, and Packer prints the `error_message`.

Packer reads values in this order, with later sources taking precedence: `PKR_VAR_` environment variables, `*.auto.pkrvars.hcl` files, and then `-var`/`-var-file` options. The Makefile always passes `-var`, so an exported `PKR_VAR_ssh_public_key` is silently ignored. The Makefile's first line uses `$(shell ssh-add -L | head -n 1 | cut -d' ' -f1,2)`. The first version wrote `$(...)` without `shell`. Make treated the whole pipeline as the name of a Make variable that didn't exist and expanded it to an empty string.

The second provisioner lists `SSH_PUBLIC_KEY=${var.ssh_public_key}` in `environment_vars` and sets `use_env_var_file = true`. The provisioner then uploads the script, plus a separate file containing `export SSH_PUBLIC_KEY='...'`, and runs `chmod +x {{.Path}}; sudo sh -c '. {{.EnvVarFile}} && {{ .Path }}'`. Root's shell sources the file and then runs the script, so `$SSH_PUBLIC_KEY` is set when `echo` appends it to `authorized_keys`. In the broken version, the `packer` user's shell sourced the file and then called `sudo`. Debian's sudo applies `env_reset`, which gave the root shell a clean environment. `echo $SSH_PUBLIC_KEY` therefore expanded to nothing and wrote a single newline, and the script exited 0. That diagnosis is inferred rather than read directly, since the broken artifact admitted no login to inspect the file; moving the sourcing inside `sudo` restored key login, which confirms it.

## Design rationale

Supplying the key at invocation time means the template no longer fixes who can log in. That decision moves to whoever runs the build. A tracked `.pkrvars.hcl` was rejected because it would simply fix one person's key again, in a second file. That reason has nothing to do with secrecy, since a public key is not a secret, which is also why `sensitive` is left off: it masks values only in Packer's own output, would not keep the key out of the artifact, and would hide the very value the log should show. Having `-var` override `PKR_VAR_` was an explicit choice not to offer a Packer-level override. An override still exists at the Make layer, because `make build SSH_PUBLIC_KEY=...` beats the Makefile's own assignment, and the second verification build used exactly that.

The key travels through `environment_vars` because interpolating `${var...}` straight into an inline line would paste it into the script as shell source code. A `'` in the value would then end the quoted string and run whatever followed it as root. Through the env file, the script refers only to `$SSH_PUBLIC_KEY`, so the key arrives as data. `use_env_var_file` is needed because this template's `execute_command` wraps everything in `sudo sh -c '...'`. With the default `{{ .Vars }}`, the default `env_var_format` of `%s='%s' ` produces `sudo sh -c 'SSH_PUBLIC_KEY='ssh-rsa AAA...' /path'`. The inner quotes close the outer ones, and the unquoted space splits the words, so `sh -c` receives only `SSH_PUBLIC_KEY=ssh-rsa`, a bare assignment that exits 0 without ever running the script. With the env file, only Packer-chosen paths sit inside the outer quotes. The `validation` rule is the only guard against an empty or malformed value: a Makefile check for an empty agent was deliberately left out. Always rebuilding, first with `--force` and later with `rm -rf output-hello`, deletes the previous artifact at the start, so a failed build leaves nothing; that was accepted for a throwaway verification image.

## Edge cases

The `^ssh-` rule rejects valid ECDSA keys, which begin with `ecdsa-sha2-`. That is a deliberate narrowing to the agent's RSA keys. `echo $SSH_PUBLIC_KEY` is unquoted, which is harmless for a two-field key but would be subject to word splitting and globbing on other values. Whether Packer escapes a `'` inside a value when it writes the env file was not tested. `make validate` runs `rm -rf output-hello` first, so validating deletes the last artifact, and the relative paths noted in `qemu/hello-image.md` mean the Makefile must run from inside `qemu/hello-key-var/` or via `make -C`. Above all, a successful build is no evidence the key arrived: nested quoting and `env_reset` each yield an exit-0 build with no usable key.

## Worked example

Take the verification build `make -C qemu/hello-key-var build SSH_PUBLIC_KEY="$(cut -d' ' -f1,2 .tmp/agent-key-2.pub)"`. Make's command-line assignment overrides the Makefile's `$(shell ...)` line, so the recipe runs `packer build --force --var "ssh_public_key=ssh-rsa <key 2 base64>" main.pkr.hcl`. Packer evaluates the template on the host. The variable is set and matches `^ssh-`, so validation passes. `${var.ssh_public_key}` resolves, and the `environment_vars` entry becomes the literal text `SSH_PUBLIC_KEY=ssh-rsa <key 2 base64>`. The qemu source then boots, exactly as in `qemu/hello-image.md`. The second provisioner uploads its script and an env file containing `export SSH_PUBLIC_KEY='ssh-rsa <key 2 base64>'`, and runs `chmod +x <script>; sudo sh -c '. <envfile> && <script>'`. In the root shell the source sets the variable, the script creates `guest` with an empty mode-600 `authorized_keys`, `echo` appends one line, and `wc -l` prints `1`; the third provisioner locks `packer` and the VM halts.

Booted with `-snapshot`, that artifact accepted an SSH login as `guest` offering only key 2 and refused one offering only key 1. The next build of the same template, with no Make override, took key 1 from the agent and produced the mirror result. Only the `-var` value differed between the two runs, and the artifacts differed in exactly that line, so the key comes from the invocation and not from anything an earlier build left behind.
