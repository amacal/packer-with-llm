# Provisioned /tmp Persistence Across a Real Boot (qemu, debian)

## Overview

This exercise takes the provisioning step from `docker/hello-image.md` (write `Hello, World!` to `/tmp/hello.txt` and install `tree`) and runs it against a real virtual disk instead of a container. The build target is `qemu`, so the artifact is a single qcow2 disk image file that boots on its own, with its own kernel and with systemd as PID 1. The base is Debian 12 (bookworm), using Debian's prebuilt `genericcloud` qcow2 from the dated directory `20260923-2610`, not an installer ISO. The question the exercise exists to answer was left open by both docker sessions: does a file a provisioner writes to `/tmp` still exist once the artifact boots standalone? On this artifact it does not, and the reason is a specific boot-time rule. The docker sessions passed that claim only because a container never boots.

This file runs above the usual 1400-word target on purpose. To get a working qemu build the session had to combine several mechanisms that are all new here: the qemu builder itself, cloud-init's NoCloud seed for first-boot access, the SSH communicator with a non-root user, `execute_command` and `shutdown_command`, a cleanup of build credentials, and systemd-tmpfiles. Each is explained once here so that later qemu sessions can cite it.

## The three possible fates of /tmp

Before the build, the session listed three things a booting Debian system could do to `/tmp`. If nothing special happens, the provisioned file is still there after boot. If systemd-tmpfiles empties `/tmp` at boot, the file is in the qcow2 but is deleted on the first boot. If a tmpfs (a RAM-backed filesystem) is mounted at `/tmp`, two different things follow depending on when the mount happens. A tmpfs mounted while the artifact boots hides the on-disk directory, so the file is shadowed rather than deleted. A tmpfs mounted during the build itself would catch the provisioner's write in guest RAM, and since the qcow2 records only what the guest writes to its virtual disk, the file would never reach the artifact at all. With `ls /tmp` alone you cannot tell deletion from shadowing. The deciding fact is whether anything is mounted at `/tmp`, which `findmnt /tmp` reports.

## Observable behavior

`packer init .` installed `github.com/hashicorp/qemu v1.1.7` into the per-user plugin store, the same mechanism `docker/hello-image.md` describes. `packer validate .` and `packer fmt -check .` both pass on the final template. `validate` refuses only while `output-hello/` already exists, with `Output directory 'output-hello' already exists`. The first build downloaded the 333 MiB base image into `~/.cache/packer/`, and later builds reused it after checking it against the pinned SHA512.

A successful build takes about 24 seconds with KVM. The log shows `Creating CD disk...` with xorriso output, `Copying hard drive...`, `Resizing hard drive...`, a forwarded SSH port, `Starting VM, booting disk image`, `Waiting for SSH to become available...`, `Connected to SSH!`, `Hello, World!`, the apt output for `tree 2.1.0-1`, three `Provisioning with shell script` lines, `passwd: password changed.`, `Gracefully halting virtual machine...` and `Converting hard drive...`. The artifact is `output-hello/packer-hello`, which has no `.qcow2` extension. `qemu-img info` reports it as qcow2 with a virtual size of 40 GiB and 1.31 GiB on disk. Two independent final builds, the second started after deleting `output-hello` and run without `-force`, each produced an artifact of exactly 1402667008 bytes.

Each artifact was booted with `qemu-system-x86_64 -snapshot` and no seed CD, and SSH as `guest` with the baked-in key worked within about six seconds. `ls -la /tmp` showed no `hello.txt`, only directories created at boot, each reporting a size of 4096, which is what an on-disk ext4 directory reports. `findmnt /tmp` printed nothing and exited 1. `tree --version` printed `tree v2.1.0`. A password-only SSH attempt as `packer` was refused with `Permission denied (publickey)` and no password prompt, and `su packer` from the `guest` session answered `su: Authentication failure`.

## Internal mechanism

With `disk_image = true`, the builder treats `iso_url` as an already-installed disk. It runs `qemu-img convert` from the cached base into `output-hello/packer-hello` and resizes it to the default 40960M. It builds a CD from `cd_files` with xorriso and attaches it as a CD-ROM with the volume label `CIDATA`. It then boots QEMU with `accel=kvm` (auto-detected), 512M of memory and one CPU, using user-mode networking with a forward from a random host port to guest port 22. `headless = true` matters here: without it the builder passes `-display gtk`, and QEMU exits at once in a container without a display.

During that boot, cloud-init's NoCloud datasource finds the `CIDATA` volume and reads `meta-data`, whose `instance-id` marks this as a first boot. It then reads `user-data`, creates `packer` with the clear-text build password and a passwordless sudo rule, and, because of `ssh_pwauth: true`, writes `PasswordAuthentication yes` into `/etc/ssh/sshd_config.d/50-cloud-init.conf`. Debian's `sshd_config` includes `sshd_config.d/*.conf` before its own `PasswordAuthentication no`. Since sshd uses the first value it reads for each keyword, the drop-in wins. Root could not have served as the build account, because the default `PermitRootLogin prohibit-password` refuses password logins for root.

The SSH communicator logs in as `packer`. For each provisioner, the shell provisioner uploads the joined inline script and launches it through `execute_command = "sudo sh -c '{{ .Vars }} {{ .Path }}'"`, so every line runs as root, `tee` included. Before that line was added, the same `apt-get update` failed with `Permission denied` and exit code 100. After the third provisioner, the builder runs `shutdown_command` over SSH. `passwd -l` invalidates only the password hash, so `packer` still exists with its sudo rule and the shutdown still works. Removing the account instead would have broken this step. Without a `shutdown_command`, the builder would kill QEMU outright, and writes still cached in guest RAM could be lost from the qcow2.

On the artifact's first standalone boot, `systemd-tmpfiles-setup.service` runs `systemd-tmpfiles --create --remove --boot --exclude-prefix=/dev`. `/usr/lib/tmpfiles.d/tmp.conf` contains `D /tmp 1777 root root -`, and the `D` type removes a directory's contents when `--remove` is given. That same unit also ran during the build boot, but before the provisioner had written anything, so the first boot that could delete `hello.txt` was the artifact's own.

## Design rationale

The cloud image was chosen over an installer ISO because the exercise is about `/tmp`, not about automating a Debian install. The CD seed was chosen over the builder's HTTP server, and costs one host tool (`xorriso`, now in `.devcontainer/Dockerfile`).

The central design idea is to keep build access separate from what the image contains. The build seed exists only to let Packer in. Its password is committed to the repository, which is acceptable only because the cleanup provisioner makes it useless in the artifact: password authentication is off over the network, and the lock blocks console and `su` logins, which never consult sshd. The `guest` account is part of the image's contents, so it is created by a provisioner in the template rather than in the seed, and it accepts only a key. Baking in the user's comment-free public key was a deliberate choice over attaching a key at verification time with a new `instance-id`. The cost is that every copy of the image trusts the holder of that key until someone rotates it. The cleanup runs as its own final provisioner, so no later step can reopen build access.

## Edge cases

Deleting `50-cloud-init.conf` makes the artifact's SSH policy depend on the base image's `sshd_config` saying `no`. That file also belongs to cloud-init, which could recreate it on a later instance, so an own drop-in sorted before it (for example `01-local.conf`) would be sturdier, and that change was deferred. `cd_files` paths and `output_directory` are resolved from the directory Packer is run in, not the template's directory, so the template works only when run from inside `qemu/hello-image/`. The packages are unpinned: one build reported `5 not upgraded` and a later one `6 not upgraded`, so identical templates can produce different contents. A `latest/` base URL paired with a fixed checksum would break once Debian publishes a new image, which is why the dated directory is used. Finally, `hello.txt` should still be inside the qcow2 itself, because the deletions happened in `-snapshot` overlays, but that was never observed directly: offline inspection needs `/dev/nbd*`, which this container lacks.

## Worked example

Trace the second final build and its check. The builder converts the cached Debian 12 base into `output-hello/packer-hello`, packs `user-data` and `meta-data` into a `CIDATA` CD, and boots. systemd-tmpfiles empties an already-empty `/tmp`, and cloud-init sees `iid-01234567` for the first time on this disk. It creates `packer` with password `packer` and NOPASSWD sudo, and writes `PasswordAuthentication yes` into the drop-in. Packer connects over the forwarded port, and the first provisioner, running as root through `sudo sh -c`, writes `/tmp/hello.txt` to the root filesystem and installs `tree 2.1.0-1`. The second creates `guest` with mode 700 on `~/.ssh` and 600 on `authorized_keys` holding the public key. The third locks `packer` and deletes the drop-in. `sudo shutdown -P now` still succeeds, because the lock left the account and its sudo rule in place, the guest flushes its cached writes and powers off, and the builder converts the disk.

Booting that file with `-snapshot`, systemd-tmpfiles applies `D /tmp` with `--remove`, so `hello.txt` is gone before any login. sshd now reads only the main config's `PasswordAuthentication no`. `guest` logs in with the key, `findmnt /tmp` finds no mount and `ls /tmp` finds no file, which together mean the file was deleted, not shadowed. A password attempt as `packer` is offered only `publickey`, and `su packer` fails against the locked hash. Every claim the template makes was thereby checked on the booted artifact.
