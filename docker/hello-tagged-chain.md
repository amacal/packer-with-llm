# Chained Post-Processors Sequence (docker, debian)

## Overview

This exercise takes the committed and tagged `ubuntu:24.04` image from `docker/hello-tagged.md` and carries it two steps further: the tagged image is saved to a tar file on disk, and a sha256 checksum of that tar is written next to it. The build target is `docker`, and the provisioning is unchanged (an inline shell provisioner writes `/tmp/hello.txt` and installs `tree`). What is new is that four post-processors run as one chain, `docker-tag`, then `docker-save`, then `artifice`, then `checksum`, inside a single `post-processors { }` block. The intuition to hold onto is that a chain does not pass files or images along; it passes artifact records, and each step sees only the record the previous step chose to return. Nearly every surprise in the session came from that one fact.

## Sequences and artifact records

The docs state that a standalone `post-processor` block and a `post-processors { }` block containing only that one step do the same thing. A standalone block is therefore a one-step sequence, and every sequence starts from the builder's own artifact. Inside a multi-step `post-processors { }` block, step two receives whatever record step one returned, step three receives step two's, and so on. The fact reused from `docker/hello-tagged.md` is that an artifact is a record describing an output, not the output itself, and that a post-processor receives one record and returns another.

Two properties of a record decide whether a chain works. The first is `BuilderId`, a string naming the component that produced the record, which is what a type check reads. docker-save (plugin v1.1.4) rejects any record whose `BuilderId` is neither `packer.post-processor.docker-import` nor `packer.post-processor.docker-tag`, so the record docker-tag returns is accepted. The second is `Files()`, the list of on-disk paths the record claims, which is what checksum iterates over. A docker image record returns `nil` from `Files()`, because an image lives in the Docker store, not in a file.

## Observable behavior

The final template, run through `make build`, commits an image, tags it `hello-tagged-chain:latest`, and leaves `.tmp/hello-tagged-chain.tar` (about 136 MB) and `.tmp/hello-tagged-chain.tar.sha256` in the exercise directory. The build summary lists five artifacts. They are the builder's image ID, the line `hello-tagged-chain:latest with tags hello-tagged-chain:latest` twice, `Created artifact from files: .tmp/hello-tagged-chain.tar`, and finally a line listing both the tar and the `.sha256` file. No line corresponds to docker-save writing the tar, even though its log prints `Saved to: .tmp/hello-tagged-chain.tar`.

Two independent builds of the final template, after `build` was made to depend on `clean`, committed `bb3ec53c…` and `5b04b056…`. Their checksum files each held exactly one line (`995d05c7…` and `56a320fe…` respectively), and `sha256sum -c` reported `hello-tagged-chain.tar: OK` both times. The hashes differ because each build commits a new image.

## Internal mechanism

docker-tag receives the builder's record, tags the image, and returns a new docker-tag record. docker-save checks that record's `BuilderId`, accepts it, runs `docker save` against the record's Id (`hello-tagged-chain:latest`) into the configured `path`, and then returns `artifact, true, false, nil`, which is the same record it received, marked "keep". That is why the tag record appears twice in the summary (once kept as docker-save's input, once as its unchanged output) and why the tar never appears as an artifact at all: from Packer's point of view the tar is a side effect.

`artifice` performs no external action. It discards the record it receives and returns a new one whose `BuilderId` is `packer.post-processor.artifice` and whose `Files()` is the list given in its `files` argument, each path globbed and checked to exist. checksum then reads `artifact.Files()`, hashes each file once per entry in `checksum_types`, and appends a line of the form hash, tab, base name to the output file. It opens that file with `O_WRONLY|O_APPEND|O_CREATE`, so it creates the file if missing but never truncates it. Its returned record lists the input files plus the output file, but the output file is added only when it did not already exist before the write.

When a step returns an error, Packer core (v1.16.1, `packer/build.go`) executes `continue PostProcessorRunSeqLoop`. The rest of that sequence is skipped, and the record the previous step returned is neither added to the results nor destroyed.

## Design rationale

The steps have to be one sequence because each depends on the previous record, not on the builder's. As four standalone blocks, checksum would receive the builder's image record, find `nil` files and write nothing. docker-save would save by image ID rather than by name, which would leave the tar's `RepoTags` empty; this last point is inferred from how `docker save` treats an ID and was not run. The ordering inside the sequence is equally forced. artifice placed before docker-save would hand docker-save a record with the artifice `BuilderId`, which its type check rejects, and artifice placed after checksum would come too late to matter.

The tar and checksum preconditions live in the Makefile: `build: clean` removes `.tmp`, then `mkdir -p .tmp` recreates it before `packer build` runs. Packer offers no place for them. docker-save does not create parent directories, and checksum has no overwrite option (its config holds only `checksum_types` and `output`). The tradeoff is that the template no longer carries its own preconditions, so `make build` is reproducible but a bare `packer build main.pkr.hcl` is not. Outputs go under `.tmp/`, which the repo's `.gitignore` pattern matches at any depth, so a 136 MB tar never reaches a commit. Every relative path resolves against the directory `packer` runs in, which the Makefile fixes as the exercise directory.

## Edge cases

The first build had no `.tmp/` directory and failed with `Error creating output file: open .tmp/hello-tagged-chain.tar: no such file or directory`, because docker-save opens its output with Go's `os.Create`, which does not create parent directories. Packer printed `Builds finished but no artifacts were created`, yet `hello-tagged-chain:latest` (`8e6c0f2eb50b`) was still in the Docker store afterwards. The tag docker-tag had applied was neither rolled back nor destroyed, only dropped from Packer's accounting. This narrows the all-or-nothing reading recorded in `docker/hello-tagged.md`, where the failing step was first in its sequence and so the builder's output was destroyed.

Placing checksum directly after docker-save, with no artifice step, produced no checksum file and no error, because the record it received listed no files and its loop never ran. After artifice was added, a second build without any cleanup appended a second line to the existing checksum file. The file then held `54b82a1c…` from the first build above `a29441a7…`, which matched the current tar, so `sha256sum -c` would have reported the first line as failed; the Makefile's `build: clean` exists to prevent exactly this. One further hazard comes from reading the artifice source and was not observed: a `files` pattern that matches nothing yields an empty file list without an error, which would make checksum silently do nothing again.

## Worked example

Take the final template and run `make build` once from `docker/hello-tagged-chain/`. Make first runs `clean`, removing `.tmp`, then `mkdir -p .tmp`, then `packer build`. The docker builder provisions the container and commits image `5b04b056…`, and its record goes into the sequence. docker-tag receives that record, applies `hello-tagged-chain:latest` to the image, and returns a docker-tag record whose Id is the name. docker-save checks the `BuilderId`, finds `packer.post-processor.docker-tag`, which it accepts, and writes `.tmp/hello-tagged-chain.tar` by name, so the tar's `manifest.json` carries `"RepoTags":["hello-tagged-chain:latest"]`. It then hands back the same tag record. artifice drops that record and returns one whose only file is `.tmp/hello-tagged-chain.tar`. checksum finds one file and one type, creates the absent `.tmp/hello-tagged-chain.tar.sha256`, writes the single line `56a320fe…` followed by a tab and `hello-tagged-chain.tar`, and returns a record listing both files. The summary therefore shows the builder ID, the tag record twice, the artifice record and the checksum record, five lines in all.

The verification proves the tar alone rebuilds the provisioned image under its name. Running `docker rmi hello-tagged-chain:latest` deleted `5b04b056…`, leaving no image of that name, and `docker load -i .tmp/hello-tagged-chain.tar` printed `Loaded image: hello-tagged-chain:latest` with the same ID `5b04b056f4a4`. `docker run --rm hello-tagged-chain:latest sh -c 'cat /tmp/hello.txt && tree --version'` then printed `Hello, World!` and `tree v2.1.1` and exited 0. This rules out plain `ubuntu:24.04` and an image left over in the store, since the name had been removed before the load.
