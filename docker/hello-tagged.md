# Tagged Docker Image via the docker-tag Post-Processor (docker, debian)

## Overview

This exercise builds the same kind of image `docker/hello-image/` produced, an `ubuntu:24.04` container provisioned with `/tmp/hello.txt` and the `tree` package and then committed, and gives it a human-readable name. The build target is `docker`, the base is the same Debian-family `ubuntu:24.04`, and the only new block is a `post-processor "docker-tag"` that names the committed image `hello-tagged:latest`. The previous exercise left behind images that `docker images` lists as `<none>:<none>`, identified only by a `sha256` image ID. After this one, the same kind of image has a row with a repository and a tag that you can run by name.

The Docker intuition needed first is about what a tag actually is. An image ID identifies the image's content and configuration. A tag is a separate name of the form `repository:tag` that points at an image ID, much like a sticky note on it. Several names can point at the same ID, and a name can later be moved to a different ID. Adding a name creates no new image, no new layer and no new ID; the existing row simply gains a name.

## Post-processors and the artifact record

A post-processor is a stage that runs after the builder has completely finished. It receives the builder's artifact and returns an artifact of its own. In Packer an artifact is a record handed from stage to stage, describing what was produced and how to find it. It is not necessarily a distinct set of bytes, and two records can describe the same image. The fetched docs place the block inside `build` ("Each `post-processor` runs after each defined build"). That placement follows the rule `docker/hello-image.md` established for `source` versus `build`: a source describes how to produce an artifact and ends at the commit, while a post-processor acts on what the build produced, just as provisioners act on the running container. Tagging cannot happen any earlier, because before the commit there is only a container, which has a container ID but no image ID for a tag to point at.

The docker-tag documentation describes itself as taking "an artifact from the docker builder that was committed". That is a constraint on the type of input it receives, and the block's position in the template doesn't express it. Its own arguments here are `repository` and the list `tags`. The page also documents `keep_input_artifact` as having no effect: "We will always retain the input artifact for docker-tag, since deleting the image we just tagged is not a behavior anyone should ever expect."

## Observable behavior

`packer validate .` and `packer fmt -check .` both passed on the final template. The first build's log ran through the same pull, run, provision, commit sequence as hello-image and printed `Image ID: sha256:af7877a23842...`. It then printed `Killing the container`, and only after that `Running post-processor:  (type docker-tag)`, followed by `Tagging image: sha256:af7877a23842...` and `Repository: hello-tagged:latest`. The final summary listed two artifacts: `Imported Docker image: sha256:af7877a23842...` and `Imported Docker image: hello-tagged:latest with tags hello-tagged:latest`. Yet `docker images hello-tagged` showed exactly one row, `hello-tagged:latest` with ID `af7877a23842`. `docker image inspect hello-tagged:latest` reported `Id` `sha256:af7877a23842...` and `RepoTags` `[hello-tagged:latest]`. So the two summary lines are two records describing one image.

The second, independent build moved the name. Afterwards `docker images hello-tagged` showed `hello-tagged:latest` on ID `1cc1271c4072`. `docker image inspect af7877a23842` still found the first image, now with `RepoTags []`. It had not been deleted; it had become dangling, meaning it still exists but no name points at it. Running `docker run --rm hello-tagged:latest sh -c 'cat /tmp/hello.txt && tree --version'` against the image the tag pointed at after build 2 printed `Hello, World!` and `tree v2.1.1 ...` with exit code 0. Because the commands are joined with `&&`, exit 0 means both checks passed.

## Internal mechanism

When the builder finishes, it hands Packer an artifact record whose type identifies what kind of thing it produced. Docker-tag checks that type before doing anything else. A committed image carries an image ID, so docker-tag tags that ID with each entry of `tags` under `repository` and returns a new record describing `hello-tagged:latest`. That new record is why the summary shows two lines. In Packer's plugin interface, a post-processor returns, alongside its new artifact, a flag saying whether to keep the input artifact and a flag saying whether its answer overrides the template's setting. Docker-tag answers "keep" and "override", so `keep_input_artifact` in the template is never consulted. Deleting the input would mean deleting image `af7877...`, which is also the image the output record names.

The export experiment exposed the type check directly. With `commit = false` and `export_path = "image.tar"` on the same `source "docker"`, the builder exported the container and killed it, and docker-tag then failed with `Post-processor failed: Unknown artifact type: packer.docker` and `Can only tag from Docker builder artifacts.` The source was still the docker builder, so docker-tag is not checking the source. It is checking the artifact type, and `packer.docker` labels the record for an exported tarball, which has no image ID to tag. Packer then reported `Builds finished but no artifacts were created.`, and no `image.tar` remained in the exercise directory. The tarball itself was never observed directly. That the builder wrote it and Packer then removed it is inferred from the log reaching `Killing the container` after the export step and the file being absent afterwards.

## Design rationale

Tagging inside the template instead of running `docker tag` afterwards keeps the name as part of the artifact's definition. The tagging step runs only when the build succeeded, and it is recorded in the same log. A post-processor failure fails the whole build, and here, because docker-tag was the first and only step and failed before it could ask Packer to keep its input, Packer destroyed the builder's complete but un-post-processed output rather than leaving it behind. A leftover tarball would let anything downstream mistake a failed build for a successful one. Leftover output can also block the next run, as `qemu/hello-image.md` already recorded for the qemu builder's refusal to reuse an existing output directory. This is narrower than "all-or-nothing", though: Packer does not roll back an external side effect a post-processor already applied successfully before a later step in the same sequence failed, as `docker/hello-tagged-chain.md` later observed with a tag that outlived a failed docker-save.

The tradeoff of a fixed tag like `latest` shows in build 2. The name always points at the newest image, but each rebuild silently strips the name from the previous image and leaves it dangling. Nothing about `hello-tagged:latest` says which build it came from, so a fixed mutable tag works against treating artifacts as immutable, identifiable versions. Old images also still accumulate, only now without names. The `keep_input_artifact` setting is shared by every post-processor yet ignored by this one, which is a small break in the uniform interface. The docs state it openly, and it is justified because for docker-tag the input and the output are the same image.

## Edge cases

The plugin at `1.1.4` still accepts the deprecated singular `tag = [...]`, so `packer validate` passed on a template using it. The current docs list only `tags`, and the template was corrected to match. A future plugin version that drops the old spelling would turn that silent acceptance into an error.

## Worked example

Trace build 1 of the final template from the commit onwards. The provisioner has written `Hello, World!` to `/tmp/hello.txt` and installed `tree 2.1.1` in the container's writable layer. `commit = true` makes the builder freeze that layer into image `sha256:af7877a23842...` and then kill the container, so when the post-processor starts, the only thing left is an image in the local store and a record describing it. Docker-tag receives that record and finds the committed-image type rather than `packer.docker`, so it proceeds. It creates the name `hello-tagged:latest` pointing at `af7877...` and returns a second record for that name, while forcing the first record to be kept. Packer prints both records, and `docker images` shows one row, because a name was added and no image was created.

Build 2 repeats the same steps and commits a new image, `1cc1271c4072`, because apt and dpkg timestamps and the commit time differ, as `docker/hello-image.md` already established. Docker-tag then points `hello-tagged:latest` at the new ID. Since a name can point at only one ID, `af7877...` loses it and is left with `RepoTags []`, still present but dangling. Running the image by name now runs `1cc1271c4072`, and the `cat` and `tree --version` check, passing with exit 0, confirms that the image behind the name contains exactly what the provisioner claimed.
