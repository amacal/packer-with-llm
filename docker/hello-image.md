# First Docker Image with a Shell Provisioner (docker, debian)

## Overview

This exercise builds the smallest complete Packer pipeline there is: take a published base image, start a container from it, run a few shell commands inside that container, and freeze the result into a new Docker image. The build target is `docker`, so the artifact is a Docker image sitting in the local Docker image store, not a bootable disk. The base is `ubuntu:24.04`, which belongs to the Debian family; the "debian" in the title names the OS family, not the exact distribution. The provisioning makes two claims that can be checked afterwards from outside: a file `/tmp/hello.txt` containing `Hello, World!`, and the `tree` package installed even though the stock base image does not ship it.

The intuition worth holding before any Packer vocabulary is the Docker one. An image is a stack of read-only filesystem layers with no kernel; a container started from it gets its own writable layer on top, every change made inside the container lands in that writable layer, and `docker rm` throws that layer away while leaving the image untouched. Turning a container's changes into something reusable therefore requires committing the writable layer as a new read-only layer, which produces a new image. Packer's Docker builder automates exactly that run, change, commit sequence. It never generates or reads a Dockerfile.

## Template anatomy

The template is `docker/hello-image/main.pkr.hcl`; Packer loads every `*.pkr.hcl` file in the directory passed to it (here `.`) as one unit. The file holds three top-level blocks with three distinct owners. The `packer {}` block contains `required_plugins`, which maps the local name `docker` to the source address `github.com/hashicorp/docker` and the exact version `1.1.4`. The `source "docker" "hello"` block is a reusable builder configuration: its first label is the builder type, which must match the local plugin name, and its second label is a free name, so the build refers to it as `source.docker.hello`. Inside it, `image = "ubuntu:24.04"` names the base and `commit = true` chooses what the artifact is. The `build` block lists `sources = ["source.docker.hello"]` and contains one `provisioner "shell"` whose `inline` array has two commands.

Each argument belongs to exactly one block, and putting one in the wrong block is a hard error. `commit` is the Docker builder's setting and therefore lives in the `source` block; `inline` is the shell provisioner's setting and therefore lives inside `provisioner "shell"`. Placing either one directly in `build` produces `An argument named "..." is not expected here.`

## Observable behavior

`packer init .` printed a single line reporting that `github.com/hashicorp/docker v1.1.4` was installed under `/home/vscode/.config/packer/plugins/github.com/hashicorp/docker/`, and nothing appeared inside the exercise directory. `packer validate .` and `packer fmt -check .` both passed on the final template. The build log ran through a fixed sequence of stages: creating a temporary directory for sharing data, pulling `ubuntu:24.04` (which reported `Image is up to date` because the digest was already cached), starting a container with `docker run ... --entrypoint=/bin/sh`, provisioning with a shell script under `/tmp/packer-shell...`, printing `Hello, World!` followed by the full `apt-get` output, `Committing the container`, an `Image ID:` line, and `Killing the container`. The final artifact line reads `Imported Docker image: sha256:...` and nothing else: no repository name and no tag.

Two independent builds of the unchanged template produced two different image IDs, `sha256:2e9ebb162ca8...` and `sha256:ca0758a933e6...`, and both images remained in the store side by side as untagged images. Running `docker run --rm <id> sh -c 'cat /tmp/hello.txt; tree --version'` against each printed `Hello, World!` and `tree v2.1.1`, verifying both claims against the artifact itself.

## Internal mechanism

Packer core does not contain any builder. Builders ship as separate plugin executables, `packer init` reads `required_plugins` and downloads the matching binary into a per-user store keyed by source address, and Packer core launches that plugin when a build needs it. Validation happens in two layers that this exercise exposed one at a time. With only a `source` block present, validation failed with `Missing build block`, a complaint from Packer core about template structure; the missing `commit` went unnoticed because an unreferenced source is never handed to any plugin. Once a `build` block referenced the source, core passed the source's configuration to the Docker builder, whose own check then reported `No instructions given for handling the artifact; expected commit, discard, or export_path`.

During the build, the Docker builder pulls the base image (the `pull` option defaults to true, so it consults the registry on every build and downloads layers only when the tag now points to a different digest), starts a long-running container, and hands each provisioner a way to execute inside it. The shell provisioner concatenates the `inline` array with newlines into a single temporary script, uploads it, and runs it with the default shebang `/bin/sh -e` as root, since the container's default user is root and the Docker builder uses no `sudo`. Because of `-e`, the first failing command aborts the script and fails the build. After all provisioners succeed, the builder commits the container's writable layer as a new image and kills the container.

## Design rationale

Builders are plugins with exact version pins so that the template, not the machine it happens to run on, decides which builder code runs; the per-user store lives outside the repository, but `packer init` on a fresh machine restores exactly `1.1.4` from the committed pin. The split between `source` and `build` separates what to start from and what artifact to produce from what to do to it, and because `sources` is a list, one provisioner written once can run against several sources in parallel, which is the basis for later Debian-versus-RHEL and Docker-versus-QEMU comparisons. The builder forces an explicit choice among `commit`, `export_path`, and `discard` because these produce different kinds of artifact (an image in the local store, a tar file on disk, or nothing).

A failed provisioner yields no image at all, never a half-provisioned one, because a partial image would look identical to a successful one while silently missing steps. The base image tag is deliberately left unpinned here: `ubuntu:24.04` can move when Ubuntu republishes the image, though never to a different release, and with `pull` defaulting to true the next build would use the newer base.

## Edge cases

The `/tmp` claim passes on Docker for a reason that does not carry over to a real machine. A container never boots, so no init system ever runs between provisioning and commit, and nothing clears `/tmp` before it is frozen into the image. A QEMU disk image that later boots standalone may mount `/tmp` as tmpfs or clean it at boot, depending on its init configuration, so the same check could fail there. Image IDs also never repeat across builds, even from an unchanged template and an unchanged base digest, because `apt-get update` and `dpkg` write timestamped files and the commit records its own creation time; a Packer build is reproducible in intent, not bit for bit.

## Worked example

Trace the second build of the final template. Packer core parses `main.pkr.hcl` and finds one build named `hello-image` referencing `source.docker.hello`, so it launches the Docker plugin installed by `packer init` at version `1.1.4` and hands it `image = "ubuntu:24.04"` and `commit = true`, which passes the builder's commit-or-export-or-discard check. The builder asks the registry what `ubuntu:24.04` points to, finds (as build 1 logged) digest `sha256:534baea6...` already cached, downloads nothing, and starts a container from it with `/bin/sh` as the entrypoint.

The shell provisioner then joins its two inline strings into one script and runs it with `/bin/sh -e` as root. The first line writes `Hello, World!` to `/tmp/hello.txt` in the container's writable layer and echoes it into the log. The second runs `apt-get update`, which fills the previously empty `/var/lib/apt/lists/`, and then `apt-get install -y tree`, which installs `tree 2.1.1`. Had either command failed, `-e` would have stopped the script and no image would exist. Both succeed, so the builder commits the writable layer on top of the base layers, reports `sha256:ca0758a933e6...`, a different ID from the first build's `sha256:2e9ebb162ca8...` because the apt and dpkg files and the commit time differ, and kills the container. Running `cat /tmp/hello.txt; tree --version` in a fresh container from that ID prints `Hello, World!` and `tree v2.1.1`, which confirms that the artifact holds exactly what the template claimed.
