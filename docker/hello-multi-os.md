# One Shell Provisioner Across Debian and RHEL Bases (docker, debian+rhel)

## Overview

This exercise takes the single-image template from `docker/hello-image.md` and makes one template produce two Docker images at once, one from `ubuntu:24.04` (Debian family) and one from `rockylinux:9` (RHEL family). Both should hold `/tmp/hello.txt` containing `Hello, World!` and the `tree` command. The point is to separate what is genuinely OS-agnostic in the provisioning (writing a file) from what is OS-specific (the package-manager workflow), and to see how a single `build` block with two sources turns into two independent, parallel builds. The builder mechanics themselves (pull, start a container, provision, commit, an untagged `sha256:` artifact) are reused unchanged from `docker/hello-image.md` and are only cited here.

## Two sources and provisioner scoping

The template is `docker/hello-multi-os/main.pkr.hcl`. It declares two source blocks, `source "docker" "ubuntu"` with `image = "ubuntu:24.04"` and `source "docker" "rocky"` with `image = "rockylinux:9"`, both with `commit = true`. The build block is named `hello-image` and lists both in `sources = ["source.docker.ubuntu", "source.docker.rocky"]`. Each entry in that list becomes its own build, and each build runs the builder's whole sequence separately, so two entries mean two containers, two provisioning passes and two committed images. Because a source block is only a reusable configuration, the same source could appear in several build blocks, which is why Packer names each build `BUILD.TYPE.NAME`, for example `hello-image.docker.rocky`, rather than just `docker.rocky`.

The OS difference is handled with the provisioner arguments `only` and `except`, which the provisioner docs describe as a way "to run a provisioner only with specific sources." Their values are source names with the `source.` prefix dropped, so the build's list says `source.docker.rocky` while a provisioner says `only = ["docker.rocky"]`. A provisioner with neither argument runs in every build. The template has three shell provisioners in this order: an unscoped one running `echo Hello, World! | tee /tmp/hello.txt`, one with `only = ["docker.ubuntu"]` running `apt-get update && apt-get install -y tree`, and one with `only = ["docker.rocky"]` running `dnf install -y tree`.

The package lines differ beyond the command name. `ubuntu:24.04` ships with an empty `/var/lib/apt/lists` (observed directly with `docker run --rm ubuntu:24.04 ls /var/lib/apt/lists`, which printed nothing), because the publisher strips the package index to keep the image small, so `apt-get install` has nothing to resolve against until `apt-get update` fills it. On Rocky, `dnf` downloads repository metadata itself when its cache is missing or expired, so there is no separate update step. `rpm` alone would not do, since it only installs or queries package files already on disk; `dnf` sits over `rpm` the way `apt-get` sits over `dpkg`. The package name `tree` happens to be the same on both families, but the software is not: Ubuntu installs `tree 2.1.1-2ubuntu3.24.04.2` and Rocky installs `tree-1.8.0-10.el9`.

## Observable behavior

`packer validate .` printed "The configuration is valid." and `packer fmt -check .` exited 0. Every log line carried either the `hello-image.docker.ubuntu` or the `hello-image.docker.rocky` prefix, with the two builds' lines interleaved. Each build printed `Hello, World!` and then only its own install output, apt's on one side and dnf's on the other. In build 1, Ubuntu finished after about 18 seconds and Rocky after 34.9 seconds, and `Wait completed after 34 seconds 891 milliseconds` matched the slower build rather than the roughly 53-second sum, showing the builds overlapped. The final section listed two artifacts, `sha256:e6ed279c…` for Ubuntu and `sha256:008cf853…` for Rocky. Build 2, run on the same template, listed `sha256:97b57b17…` and `sha256:f4a4439a…` and ended with exit code 0. Running each of the four images with `docker run --rm` showed `ID=ubuntu` or `ID="rocky"` in `/etc/os-release`, `Hello, World!` in `/tmp/hello.txt`, `tree v2.1.1` with `dpkg -s tree` reporting `install ok installed` on the Ubuntu images, and `tree v1.8.0` with `rpm -q tree` reporting `tree-1.8.0-10.el9.x86_64` on the Rocky images.

## Internal mechanism

Packer core reads the build block, sees two source references and creates one build per reference, launching them in parallel by default. Which provisioners run is decided from the template alone, before any command reaches the container: each build walks the provisioner list in declaration order and compares its own source name, such as `docker.rocky`, against each provisioner's `only` and `except` lists, skipping any provisioner that excludes it. So the Ubuntu build runs the echo provisioner and then the apt provisioner, and the Rocky build runs the echo provisioner and then the dnf provisioner. Declaration order matters as soon as one step depends on another; had the unscoped step been `tree /tmp > /tmp/listing.txt`, it would have to be declared after both scoped installs.

Failure is per build. Each inline script runs under `/bin/sh -e`, as established in `docker/hello-image.md`, and Packer checks the remote script's exit status: a non-zero status fails that provisioner, the build runs its cleanup, kills the container and commits nothing. `-e` matters for a command that fails unexpectedly partway through the script, because it turns that failure into a non-zero exit; an explicit `exit 1` ends the script with a non-zero status on its own. The other build carries on regardless, and `packer build` then exits with 1 if any build failed, while the successful builds' images stay in the Docker store. Image IDs differ between runs for the reason given in `docker/hello-image.md`, now with the dnf cache and rpm database adding to the varying files alongside the commit's own creation time.

## Design rationale

The alternative design was a single inline script that reads `/etc/os-release` and branches between apt and dnf at runtime. Scoping with `only` was chosen because the OS knowledge then lives in the template, where a reader can see what each source gets and where the build log shows, per prefix, which provisioner ran. The cost shows up when a source is added without a matching provisioner. With `only`, a hypothetical `docker.alpine` source would run only the echo step, succeed and commit an image without `tree`, so nothing in the log or the exit code would reveal the gap. A runtime script whose `else` exits non-zero would fail loudly instead, but only if written that way, with the OS logic hidden where Packer cannot see it. What compensates for the silent case in this exercise is the verification step: checking each artifact for `tree` through its own package database catches a missing install that a green build cannot.

## Edge cases

A deliberate failure run used `dnf install -y treee`. Ubuntu still committed `sha256:0ed5b3ea…`, Rocky logged `Error: Unable to find a match: treee` and `Script exited with non-zero exit status: 1. Allowed exit codes are: [0]`, the final section listed only the Ubuntu artifact under "artifacts of successful builds", and `packer build` exited 1. A non-zero overall exit therefore does not mean that no images were produced. Separately, the `/tmp/hello.txt` result is still only Docker evidence, now on a RHEL base as well as a Debian one; a container never boots, so it says nothing about whether `/tmp` survives a real boot of a qemu disk image.

## Worked example

Trace the Rocky build of build 2 on the final template, which Packer starts side by side with the Ubuntu build. The docker plugin receives `image = "rockylinux:9"` and `commit = true`, finds digest `sha256:d7be1c09…` already cached (`Image is up to date`) and starts a container with `/bin/sh` as its entrypoint. The build now walks the three provisioners in order. The first has no `only` or `except`, so it runs and writes `Hello, World!` into `/tmp/hello.txt` in the container's writable layer. The second has `only = ["docker.ubuntu"]`, which does not contain `docker.rocky`, so it is skipped without anything being sent to the container. The third has `only = ["docker.rocky"]`, so it runs `dnf install -y tree`; dnf downloads the BaseOS, AppStream and Extras metadata, imports the Rocky GPG key and installs `tree-1.8.0-10.el9`. The script exits 0, so the builder commits the writable layer as `sha256:f4a4439a…`, a different ID from build 1's `sha256:008cf853…` because the dnf cache, rpm database and commit time differ, and then kills the container. The build finishes after 35.3 seconds, the Ubuntu build having already finished on its own path, so `Wait completed` shows 35.3 seconds and the exit code is 0. Running `docker run --rm f4a4439a sh -c 'grep "^ID=" /etc/os-release; cat /tmp/hello.txt; tree --version; rpm -q tree'` prints `ID="rocky"`, `Hello, World!`, `tree v1.8.0` and `tree-1.8.0-10.el9.x86_64`, which confirms that the artifact came from the RHEL base and that its `tree` came through that OS's own package manager.
